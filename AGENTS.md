# AGENTS.md

## Purpose

- Black-box system, multi-tenant and load tests for Project Continuum, written for Grafana k6. They run against a live stack (docker-compose or a cluster) and never import platform code.

## Ownership

- `docker/`: the stack under test. `docker-compose.yml` is a copy of `continuum-feature-template/docker/docker-compose.yml` with one change: the four platform images (api-server, orchestration-service, message-bridge, credentials-server) use `${CONTINUUM_PLATFORM_VERSION:-0.0.23}`. `postgres/`, `temporal/` and `mosquitto/` are copies of the config next to it.
- `lib/`: helpers shared by every suite (`config`, `tenant`, `workflows`, `capabilities`, `metrics`, and the pure `util.js`).
- `suites/`: k6 scripts. `smoke.js`, `tenancy/isolation.js` and `api/{workflow,runs,schedules,node-explorer,data,credentials,cluster-manager}.js` exist today. Scope: the core platform only. The workbench UI is planned; the cloud-gateway and knime-scheduler are not part of the core platform and have no suites.
- `fixtures/workflows/`: workflow models posted to the api-server.
- `test/`: `node --test` unit tests for the pure helpers in `lib/` (`util`, `guard`, `loadplan`, `fairness`, `report`).
- Load: `suites/load/profile.js` (throughput | stress | spike | soak, chosen by `PROFILE`) and `suites/load/noisy-neighbor.js`. Pure logic lives in `lib/loadplan.js` (phases, scenarios, thresholds), `lib/guard.js` (the safety guard), `lib/fairness.js` and `lib/report.js` (table and findings); `lib/loadrun.js` is the k6-side glue.
- `README.md`: user-facing setup and usage. Keep it in sync with the suites, env vars and Make targets listed here.

## Local Contracts

- A tenant is only the `x-continuum-user-id` header. Make every request through `lib/tenant.js` so it carries the header and the `tenant:<id>` metric tag.
- Tenant ids and workflow names are prefixed `systest-<runId>` / `/systest/<runId>/`. Workflow runs cannot be deleted through the API, so this prefix is the only way to find test data afterwards.
- Base URLs come from env vars in `lib/config.js` (`API_SERVER_URL`, `CREDENTIALS_URL`, ...). Never hardcode a port: the api-server is 8080 in compose and 8081 in the IntelliJ run configs.
- Isolation checks are hard failures: tenant B must get 404 (or an empty list) for anything tenant A owns. `isolation_violations` must stay 0.
- Node output (`/api/v1/data/...`) is addressed by the Temporal RUN id, read from the stored path `{remote}<runId>/<nodeId>/output.<port>.parquet` (`parseStoredPath` / `outputsOf` in `lib/util.js`), never by the workflow id the start call returns.
- A suite that only proves a denied tenant is denied also passes when nobody can read anything. Every isolation check on a resource needs a matching check that its owner can still read it.
- Behaviour that is wrong today goes through `knownGap()` in `lib/checks.js`: assert the status the platform SHOULD return; a miss logs `KNOWN GAP` and counts in `known_gaps` but does not fail. Never assert a bug (a 500) as correct. When the platform is fixed, turn the call into a normal `check`.
- Use `tenant()` for every call: it marks 2xx-4xx as expected responses, so `http_req_failed` counts only 5xx and network errors.
- Each suite deletes what it creates (schedules, credentials) in a `finally`, even on failure. Workflow runs cannot be deleted; they keep the `systest-<runId>` prefix.
- `docker/docker-compose.cluster-manager.yml` adds the optional cluster-manager; it is a separate overlay so the main compose file stays a copy of the template's. `suites/api/cluster-manager.js` skips itself when the service is unreachable.
- The cluster-manager suite has two tiers. Tier 1 may only send requests the service rejects BEFORE it calls Kubernetes (a request that looks valid would create a real pod on a cluster, or answer 500 without one). Tier 2 (`CLUSTER_MANAGER_K8S=true`) creates real pods: at most one workbench per run, small requests, deleted in a `finally`.
- Keep k6-specific code (`k6/http`, `k6/metrics`, `open()`) out of `lib/util.js`, which must stay unit-testable with plain node.
- `docker/.env` pins the Postgres and Temporal image versions. It is copied from the template repo and is not read or generated by tooling here.
- Tests that need an optional feature worker must check `lib/capabilities.js` first and skip, not fail, when the nodes are absent.
- Load profiles must stay opt-in and must not run against a shared environment by accident.
- Every load suite calls `requireLoadAllowed()` first in `setup()`: it fails unless `ALLOW_LOAD=true` AND every target host is in `LOAD_ALLOWED_HOSTS` (default localhost, 127.0.0.1, matched on the exact host, never a prefix). Never weaken it or add a default host that is not a developer machine. A load run creates workflows, object-store files and rows that cannot be deleted through the API.
- Load uses arrival-rate executors, one k6 scenario per phase, so each phase has its own `scenario:<name>` tagged numbers. A k6 sub-metric is only in the end-of-test data when a threshold names it, so `thresholdsFor` declares a report-only (`>=0`) threshold for everything the report prints. When a phase is not gated it must still be listed.
- A workflow that fails to START must still count as a failed workflow in `workflow_success` (`timedWorkflow` does this); otherwise a saturated start path vanishes from the success rate.
- Pass/fail for fairness is a k6 threshold on `fairness_within_limit`, fed per workflow. `handleSummary` cannot change k6's exit code, so a verdict computed only there would never fail a run.
- A phase or ratio with no data is "unknown" (`-`, `undefined`), never 0: an empty phase must not read as a fast one, and a missing fairness ratio is never a pass.

## Work Guidance

- When the template compose changes, copy it over again and re-apply the `CONTINUUM_PLATFORM_VERSION` substitution on the four platform images; make no other hand edits to `docker/docker-compose.yml`.
- Test another platform release with `CONTINUUM_PLATFORM_VERSION=0.0.24 make up`. Set it before every `make` target that touches the stack, or compose falls back to the default and recreates containers on the old version.
- Assert status codes and the fields the suites rely on, not whole response bodies.
- A run's state comes from its record, `GET /api/v1/workflow-runs/{workflowId}` (`getStatus` / `waitForTerminal` in `lib/workflows.js`). Final statuses are `FINISHED`, `FAILED`, `CANCELLED` and `TERMINATED`; a successful run is `FINISHED`. The message-bridge writes the record asynchronously, so poll, do not fail on the first read.

## Verification

- `npm test` (unit tests for `lib/util.js`) and `npm run check` (syntax check of every script). Both need only node.
- `make up && make smoke && make tenancy` against a clean compose stack. Needs Docker and k6.
