# AGENTS.md

## Purpose

- Black-box system, multi-tenant and load tests for Project Continuum, written for Grafana k6. They run against a live stack (docker-compose or a cluster) and never import platform code.

## Ownership

- `docker/`: the stack under test. `docker-compose.yml` is a copy of `continuum-feature-template/docker/docker-compose.yml` with one change: the four platform images (api-server, orchestration-service, message-bridge, credentials-server) use `${CONTINUUM_PLATFORM_VERSION:-0.0.23}`. `postgres/`, `temporal/` and `mosquitto/` are copies of the config next to it.
- `lib/`: helpers shared by every suite (`config`, `tenant`, `workflows`, `capabilities`, `metrics`, and the pure `util.js`). The Kotlin language-server suites add plain-Node `.mjs` helpers: `theia-client`, `theia-wire`, `ws-frames` (Socket.IO + Theia channel multiplexer client), `lsp-session` (JSON-RPC on one channel), `lsp-stdio` (JSON-RPC over a language server's stdin/stdout), `lsp-capabilities` (what an `initialize` answer promises, and a probe request per promise), `kotlin-script` (the context document and hidden-header line mapping, and `reportedContextFromFeatureSource`: the names the Kotlin Script node reports, built from the real `ScriptFlowVariables.kt` of the sibling `continuum-feature-base`, or `FEATURE_BASE_DIR`; the suites SKIP what needs it when the source is absent), `proc-info` (`/proc` readers), `image-probe` (docker/image output parsers) and `runner` (check recorder). Everything pure in them is unit-tested; `theia-client.mjs` (sockets) is verified live only.
- `suites/ui/`: browser (Puppeteer, plain Node ESM, not k6) scenarios for the workbench. `loops.mjs` covers Loop canvas membership, live resizing, selected corner controls, and exact drop-position preservation for real mouse drags in every direction and over another node; it saves edits through the workbench before reading `.cwf` state. `loops-dialog.mjs` covers the Loop condition dialog (CEL/builder, validation, shapes), real mouse click-then-drag, dark/light theme presentation, and a real iterating run in the viewer, including an explicit assertion that a member shows its last-iteration Success status (`ONLY=visual|dialog|shapes|run|design|dragout|mouse|r5theme|collapse|payload|dbl`; `proxy.mjs` is a streaming reverse proxy (:3013, forwards /api-server, /credentials-server, /mqtt WebSocket to mosquitto :31884; use with `PASSTHROUGH=1 WORKBENCH_URL=http://127.0.0.1:3013`); the Loop node descriptor is fetched from the node explorer, nothing is read from /tmp; `NETLOG=<regex>` logs matching API responses); `lib.mjs` (also `flags.failValidate` to simulate an unreachable validation service) is the shared driver (headless launch, request-interception proxy to api-server/credentials-server when the workbench has none, palette drag, workflow save, `.cwf` readback). Env: `WORKBENCH_URL` (default http://127.0.0.1:3002), `API_SERVER_URL`, `CREDENTIALS_URL`, `PUPPETEER_PATH`, `SHOT_DIR`; `ONLY=run|looprun` runs a single probe. Needs the stack up and a workbench build; takes ~5 min.
- `suites/ui/kotlin-lsp.mjs`: browser scenarios for Kotlin language-server support (`ONLY=<name>[,<name>]`; names `first-open`, `completion`, `valid`, `diagnostics`, `hover`, `sighelp`, `unclosed`, `header`, `fallback`, `kill-early`, `channel`, `twodialogs`, `twocontexts` (two nodes whose contexts declare the same type name), `no-context` and `bad-context` (a node that reports nothing usable gets a plain editor), `save`, `rest-unchanged`, `kt-file`, `journey` and the opt-in `hung`). It writes its own `.cwf` (the Kotlin Script node schema copied from `KotlinScriptNodeModel.kt`), so it needs only a workbench, NOT the platform stack, and it does not use the proxy of `lib.mjs` `launch()`. Env: `WORKBENCH_URL`, `SHOT_DIR` (absolute path outside version control), `SHOT_PREFIX` (screenshot name prefix, one per run keeps earlier evidence), `BACKEND_PID` (the workbench backend; Kotlin server processes are counted by parentage under it: `bridge` = child of the backend, `extension` = the fwcd.kotlin extension's; default: the listener of the URL's port), `BACKEND_LOG`, `THEIA_CONFIG_DIR` (to read the fwcd.kotlin first-run marker), `READY_TIMEOUT_MS`, `CHIP_TIMEOUT_MS`, `KT_EXT=kt|kts`. It reaches Monaco and the app stores through webpack-require, so it needs a development (non-minified) workbench build. Scenarios that need a cold server (`first-open`, `rest-unchanged`, `journey`, `channel`, `kt-file`) end an idle Kotlin JVM under `BACKEND_PID` (SIGTERM, the Kotlin JVM only), and `fallback`, `kill-early` and `hung` kill or freeze it: run them only against a workbench you own. `channel` holds the channel-open message back inside the test browser (fault injection, nothing is changed on the server).
- `suites/api/kotlin-lsp-bridge.mjs`: black-box checks (plain Node 20+, no k6, no platform stack) of the workbench's Kotlin language-server bridge, the Theia channel `/services/language-server/kotlin-script`. Groups `lifecycle`, `coldwindow` (a script opened around the moment a cold server becomes ready: diagnostics arrive and the first edit is applied, also a mistake typed into a clean script as the first edit), `handshake`, `offline`, `diagnostics` (includes: `initialize` promises only methods the bridge serves), `packaging`, `documents`, `context` (the reported names as a hidden context document opened and acknowledged before the script: `flow.` completion, KDoc hover, type mismatch, valid silence, two contexts isolated, non-virtual context URI refused, closing frees it), `security`, `leak`, `memory`, `protocol` and the opt-in `exhaustion` (heap full: does the bridge replace the server?) (`ONLY=<group>[,<group>]`). Env: `WORKBENCH_URL`, `BACKEND_PID`, `IDLE_TIMEOUT_SECONDS`, `IDLE_CHECKS`, `EXPECT_LS_HOME`, `LEAK_PROBE_DIR`, `LS_MEMORY_LIMIT_MB`, `LS_XMX_MB`, `START_TIMEOUT_SECONDS`, `LS_OPEN_DOCUMENTS`, `EXHAUSTION_DOCUMENTS`, `EXHAUSTION_WATCH_SECONDS`, `COLDWINDOW_OFFSETS_MS`, flag `--offline`. The suite header explains the wire framing.
- `suites/api/kotlin-lsp-image.mjs`: black-box checks of the production workbench image through the docker CLI (plain Node, needs Docker, no k6). Groups `image`, `download`, `launcher` (the start launcher over stdio with no network), `seedscript` (the source copy of the seed script run on the host: byte-order mark, comments, unreadable file; needs `WORKBENCH_SOURCE_DIR`), `seed` (the same in the image, also JSONC, byte-order-mark and unreadable settings files, and through the entrypoint), `asis` and the opt-in `experiment`, `default-idle`, `exhaustion`, `pod-limit`. It copies `lib/*.mjs` and the bridge suite into a container started `--network none` as uid 1000 and runs them there. Env: `IMAGE` (required), `BASELINE_IMAGE`, `WORKBENCH_SOURCE_DIR`, `NAME_PREFIX`, `BRIDGE_TIMEOUT_MINUTES`, `POD_LIMIT_GIB`, `ONLY`.
- `suites/` (k6): k6 scripts. `smoke.js`, `tenancy/isolation.js` and `api/{workflow,runs,schedules,node-explorer,data,credentials,cluster-manager}.js` exist today. Scope: the core platform only. The workbench UI is planned; the cloud-gateway and knime-scheduler are not part of the core platform and have no suites.
- `fixtures/workflows/`: workflow models posted to the api-server.
- `test/`: `node --test` unit tests for the pure helpers in `lib/` (`util`, `guard`, `loadplan`, `fairness`, `report`, and the Kotlin suites' `ws-frames`, `theia-wire`, `lsp-session`, `lsp-stdio`, `lsp-capabilities`, `kotlin-script`, `proc-info`, `image-probe`, `runner`).
- Load: `suites/load/profile.js` (throughput | stress | spike | soak, chosen by `PROFILE`) and `suites/load/noisy-neighbor.js`. Pure logic lives in `lib/loadplan.js` (phases, scenarios, thresholds), `lib/guard.js` (the safety guard), `lib/fairness.js` and `lib/report.js` (table and findings); `lib/loadrun.js` is the k6-side glue.
- `README.md`: user-facing setup and usage. Keep it in sync with the suites, env vars and Make targets listed here.

## Local Contracts

- A tenant is only the `x-continuum-user-id` header. Make every request through `lib/tenant.js` so it carries the header and the `tenant:<id>` metric tag.
- Tenant ids and workflow names are prefixed `systest-<runId>` / `/systest/<runId>/`. Workflow runs cannot be deleted through the API, so this prefix is the only way to find test data afterwards.
- Base URLs come from env vars in `lib/config.js` (`API_SERVER_URL`, `CREDENTIALS_URL`, ...). Never hardcode a port: the api-server is 8080 in compose and 8081 in the IntelliJ run configs.
- Isolation checks are hard failures: tenant B must get 404 (or an empty list) for anything tenant A owns. `isolation_violations` must stay 0.
- Node output (`/api/v1/data/...`) is addressed by the Temporal RUN id, read from the stored path `{remote}<runId>/<nodeId>/output.<port>.parquet` (`parseStoredPath` / `outputsOf` in `lib/util.js`), never by the workflow id the start call returns.
- A suite that only proves a denied tenant is denied also passes when nobody can read anything. Every isolation check on a resource needs a matching check that its owner can still read it.
- Behaviour that is wrong today goes through `knownGap()` in `lib/checks.js`: assert the status the platform SHOULD return; a miss logs `KNOWN GAP` and counts in `known_gaps` but does not fail. Never assert a bug (a 500) as correct. When the platform is fixed, turn the call into a normal `check`.
- Use `tenant()` for every call: it marks 2xx-4xx as expected responses, so `http_req_failed` counts only 5xx and network errors.
- Each suite deletes what it creates (schedules, credentials) in a `finally`, even on failure. Workflow runs cannot be deleted; they keep the `systest-<runId>` prefix.
- `docker/docker-compose.cluster-manager.yml` adds the optional cluster-manager; it is a separate overlay so the main compose file stays a copy of the template's. `suites/api/cluster-manager.js` skips itself when the service is unreachable.
- The cluster-manager suite has two tiers. Tier 1 may only send requests the service rejects BEFORE it calls Kubernetes (a request that looks valid would create a real pod on a cluster, or answer 500 without one). Tier 2 (`CLUSTER_MANAGER_K8S=true`) creates real pods: at most one workbench per run, small requests, deleted in a `finally`.
- Keep k6-specific code (`k6/http`, `k6/metrics`, `open()`) out of `lib/util.js`, which must stay unit-testable with plain node.
- `docker/.env` pins the Postgres and Temporal image versions. It is copied from the template repo and is not read or generated by tooling here.
- Tests that need an optional feature worker must check `lib/capabilities.js` first and skip, not fail, when the nodes are absent.
- Load profiles must stay opt-in and must not run against a shared environment by accident.
- Every load suite calls `requireLoadAllowed()` first in `setup()`: it fails unless `ALLOW_LOAD=true` AND every target host is in `LOAD_ALLOWED_HOSTS` (default localhost, 127.0.0.1, matched on the exact host, never a prefix). Never weaken it or add a default host that is not a developer machine. A load run creates workflows, object-store files and rows that cannot be deleted through the API.
- Load uses arrival-rate executors, one k6 scenario per phase, so each phase has its own `scenario:<name>` tagged numbers. A k6 sub-metric is only in the end-of-test data when a threshold names it, so `thresholdsFor` declares a report-only (`>=0`) threshold for everything the report prints. When a phase is not gated it must still be listed.
- A workflow that fails to START must still count as a failed workflow in `workflow_success` (`timedWorkflow` does this); otherwise a saturated start path vanishes from the success rate.
- Pass/fail for fairness is a k6 threshold on `fairness_within_limit`, fed per workflow. `handleSummary` cannot change k6's exit code, so a verdict computed only there would never fail a run.
- A phase or ratio with no data is "unknown" (`-`, `undefined`), never 0: an empty phase must not read as a fast one, and a missing fairness ratio is never a pass.
- A check that proves a negative ("this was refused", "nothing leaked") needs a nearby positive that proves the probe could have seen it. The Kotlin bridge suite pairs each refusal with a request on the connection's own document that is served.
- The Kotlin suites never import platform code and never write to the workbench's own folders: documents are named `systest-<runId>-<n>` and live only in the server's memory; the leak probe plants one `.kt` file per `LEAK_PROBE_DIR` folder and removes it in a `finally`.
- Process checks (`lifecycle`, `packaging`, `memory`, the private-directory check) read `/proc` and need the suite to run where it sees the backend's processes. When it cannot, they print `SKIP ... NOT VERIFIED: <reason>`; never turn a skip into a pass. Inside a container, run the suite as the backend's own uid: a container's root cannot read another user's `/proc/<pid>/fd` or `cwd` (no `CAP_SYS_PTRACE`).
- `kotlin-lsp-image.mjs` creates only containers and volumes named `<NAME_PREFIX>-<runId>-<role>` and removes only names it made (`isOwnedName`). It never prunes, never uses `down -v`, never builds an image and runs every container with `--network none`. Opt-in groups (`experiment`, `default-idle` ~11 min, `exhaustion`, `pod-limit`) stay behind `ONLY=`.

## Work Guidance

- When the template compose changes, copy it over again and re-apply the `CONTINUUM_PLATFORM_VERSION` substitution on the four platform images; make no other hand edits to `docker/docker-compose.yml`.
- Test another platform release with `CONTINUUM_PLATFORM_VERSION=0.0.24 make up`. Set it before every `make` target that touches the stack, or compose falls back to the default and recreates containers on the old version.
- Assert status codes and the fields the suites rely on, not whole response bodies.
- A run's state comes from its record, `GET /api/v1/workflow-runs/{workflowId}` (`getStatus` / `waitForTerminal` in `lib/workflows.js`). Final statuses are `FINISHED`, `FAILED`, `CANCELLED` and `TERMINATED`; a successful run is `FINISHED`. The message-bridge writes the record asynchronously, so poll, do not fail on the first read.

## Verification

- `npm test` (unit tests for the pure helpers in `lib/`) and `npm run check` (syntax check of every script). Both need only node.
- `make up && make smoke && make tenancy` against a clean compose stack. Needs Docker and k6.
- `make kotlin-lsp` (needs a running workbench backend) and `make kotlin-lsp-image` (needs Docker and a local workbench image): plain Node, no k6, no platform stack.
